S06 — Deterministischer Deadlock + 181 Thread-Leaks: Die alte QueuedObserver startet pro Message einen Drain-Task (Thread-Armee). SendCompleted → OnCompleted drainet inline im Aufrufer-Thread mit while (Dequeue) — ohne Ende-Kondition. Wenn die Queue leer ist (Army hat sie entleert) und m_IsQuit=false, blockieren alle 182 Threads (181 Army + 1 Aufrufer) ewig in BlockingQueue.Dequeue → Monitor.Wait. Stack im Dump:

Monitor.Wait → BlockingQueue.Dequeue (BlockingQueue.cs @ 127)
→ QueuedObserver.OnCompleted (SimpleObservable.cs @ 332)
→ Observable.SendCompleted (SimpleObservable.cs @ 140)
→ Scenarios.OnCompletedOrder (Scenarios.cs @ 283)


S02 — Throughput-Kollaps der Army: 64/6000 in 30 s ≈ 2/s. Ursache: jeder Enqueue weckt per PulseAll alle ~180+ auf demselben Monitor wartenden Army-Threads → Monitor-Kavaleade; pro Item hunderte wecke/Context-Switches. Bei Dispose wird der Backlog per Clear() still verworfen (Datenverlust ohne Hinweis).

S08 — Gleicher Ref-Leak wie neu: Subscribe überschreibt m_Unsubscriber ohne Dispose. Der Leck-Defekt ist also alt — nie behoben. Die neue Worker-Architektur löst S06/S02, aber bringt S04/S09/S10 mit.

- Enqueue(Timeout.Infinite) ohne konfigurierbare Backpressure-Politik.
- Clear() bei Unsubscribe/Dispose verwirft Backlog still.
- Aboschicht: nicht-aufgeräumte Referenz (S08).

Dann in World:

		Systems.ClearData ();

### Theoretisches Problem

Nach ClearData() beginnen neue Entities wieder mit der ID = 1.

Wenn ein Consumer des ECS sich Referenzen auf Entities speichert (das sollte er eigentlich nicht tun, aber man kann es nicht ausschliessen), dann erhält er be der nächsten Auflösung unter Umständen eine völlig andere Entity zurück - aber er merkt nichts davon und es gibt keinen Fehler. Das ist gefährlich.


SummerGUI nutzt für Widget ein ähnliches Pattern:

Nächster Test: Threadsafty des ECS-Systems testen.

Real-World-Szenario:

Vom Server kommen neue und geändserte Daten. Diese werden in einem Worker-Thread (später in Observern) verarbeitet.

Das könnte sogar parallel in mehreren Workern geschehen, denn die Daten kommen vom Server völlig asynchron und werden asynchron verarbeitet.

Im GUI-Thread laufen mehrere Rendering-Systeme und greifen auf diese Daten zu.
Die Rendering-Systeme sollten möglichst nicht oder nur extram kurz blockieren, denn in der OpenGL-Anwendung wird mit 30pder 60 FPS gerendert.

Bottlenecks (alle im Code verifiziert):
1. Jede Struktur-Operation (Create/Add/Remove) re-evaluert die System-Mitgliedschaft für jedes System — das ist die eigentliche „ECS-Tax“ und erklärt die 5–17×-Lücke gegen die POCO-Iteration.
2. ThreadSafeHashSet der Memberschafts-Sets = harte lock → Concurrency-Hotspot.
3. Find<T> macht eine redundant zweite Dictionary-Probe.
4. Per-Entity-Container + Finalizer → die 635 B/Ent.
